# ТЗ v1.0 — Мобильное приложение интернет-магазина канцтоваров

**Дата:** 14.08.2026 · **Команда:** 2 разработчика + Claude (Opus/Sonnet) · **Статус:** к утверждению

---

## 0. Кратко

Мобильное приложение iOS + Android (Flutter) в UX-логике Ozon / Kaspi Магазина для розничного магазина канцтоваров с ассортиментом **4000+ SKU**: каталог с категориями, поиск, корзина, онлайн-оплата, заказы, бонусная программа с гибкими уровнями, промокоды, рекомендации. Дизайн — минимализм.

Разработка ведётся **двумя параллельными треками** (Трек A — бэкенд/админка/инфраструктура, Трек B — мобильное приложение) по принципу **contract-first**: единственный источник правды — `openapi.yaml`. Вся разработка — через Claude, правила работы с ним зафиксированы в разделе 3.5.

---

## 1. Цели и границы

**Цель MVP:** покупатель находит любой из 4000+ товаров через поиск или категории, оформляет заказ, оплачивает онлайн, получает фискальный чек и отслеживает статус. Бизнес управляет каталогом, остатками, ценами, заказами, промокодами и бонусами через веб-админку. Товары загружаются массово из XLSX.

**В MVP НЕ входит** (вторая очередь, раздел 5):
- отзывы и рейтинги товаров
- казахская локализация (i18n-каркас закладываем с первого дня, но перевод — потом)
- поиск по фото
- маркетинговые push-рассылки из админки
- рекомендации «с этим покупают» на основе истории заказов (в MVP — упрощённые «похожие товары»)
- тёмная тема
- веб-витрина
- офлайн-режим (кроме кэша картинок)

## 2. Треки и зоны ответственности

| | Трек A — Backend / Admin / Infra | Трек B — Mobile (Flutter) |
|---|---|---|
| **Кто** | Разработчик с DevOps-опытом (k3s, GitLab CI) | Второй разработчик |
| **Отвечает за** | FastAPI-бэкенд, PostgreSQL, Redis, MinIO, админ-панель (React), интеграции: оплата, ОФД-чеки, SMS, FCM-отправка; деплой staging/prod, CI/CD, бэкапы | Flutter-приложение целиком: все экраны, навигация, состояние, работа с API, push-приём, сборки iOS/Android, публикация beta |
| **Репозиторий** | `shop-backend` (внутри: `/api`, `/admin`, `/deploy`) | `shop-app` |

**Общие артефакты (правки только через MR с апрувом обоих):**
- `openapi.yaml` — контракт API (лежит в `shop-backend/contracts/`)
- `design_tokens.md` — цвета, типографика, отступы (раздел 8)
- этот файл ТЗ

**Правило границы:** Трек B никогда не ждёт Трек A — до готовности реального эндпоинта работает на mock-сервере по контракту. Трек A никогда не меняет контракт молча — только MR в `openapi.yaml`.

## 3. Процесс параллельной разработки

### 3.1 Спринт 0 (дни 1–3, вместе)
1. Утвердить это ТЗ и закрыть «Открытые вопросы» (раздел 14).
2. Трек A: скелет `openapi.yaml` по разделу 11 → ревью Трека B → тег `v1.0`.
3. Зафиксировать `design_tokens.md` и список экранов (раздел 8).
4. Завести репозитории, GitLab CI, поднять mock-сервер.
5. Трек A: staging-namespace в k3s, домены `api-staging.…` / `admin-staging.…`.

### 3.2 Mock-сервер
- Инструмент: **Prism** (`prism mock contracts/openapi.yaml`) + примеры ответов в самом контракте (`example:` на каждый эндпоинт — обязательны).
- Трек A держит mock в актуальном состоянии; Трек B указывает `API_BASE_URL` через flavor (mock / staging / prod).

### 3.3 Git и CI
- GitLab, trunk-based: `main` + короткие feature-ветки, MR обязателен, ревьюит второй разработчик (быстрое ревью, не блокирующее: апрув в течение рабочего дня).
- CI backend: lint (ruff) → tests (pytest) → build image → deploy staging (автодеплой из `main`).
- CI mobile: `flutter analyze` → tests → сборка apk (артефакт на каждый MR).
- Точка интеграции — конец каждой недели: Трек B переключает flavor mock → staging и прогоняет свои экраны на живых данных, расхождения фиксируются issue немедленно.

### 3.4 Договорённости по API (фиксируем в контракте)
- База: `/api/v1`, JSON, даты ISO 8601 UTC, деньги — **целые тенге (int)**.
- Пагинация: `?page=1&limit=24` → ответ `{items: [...], meta: {page, limit, total}}`.
- Ошибки: `{"error": {"code": "OUT_OF_STOCK", "message": "…"}}` + корректные HTTP-статусы. Коды ошибок — enum в контракте.
- Auth: `Authorization: Bearer <JWT>`; публичные эндпоинты (каталог, поиск) работают без токена.
- Цены и остатки клиенту не доверяем никогда: пересчёт только на сервере (см. 4.7).

### 3.5 Правила работы с Claude
1. В каждом репо — `CLAUDE.md`: стек, команды запуска/тестов, конвенции, ссылки на ТЗ и контракт.
2. Каждая фича — отдельная сессия Claude Code. В контекст: соответствующий раздел этого ТЗ + `openapi.yaml` (+ `schema.sql` для бэка).
3. Claude **не имеет права изменять контракт** «по ходу» — если для фичи нужен новый эндпоинт/поле, сначала MR в `openapi.yaml`, апрув, потом код.
4. Мелкие коммиты, зелёный CI перед мержем. Сгенерированный код читаем сами: особенно всё, что касается денег, бонусов и статусов заказа.
5. Тесты — тоже через Claude, но сценарии денег/бонусов (раздел 4.11–4.12) проверяем руками по чек-листу раздела 13.

## 4. Функциональные требования MVP

### 4.1 Авторизация
- Вход по номеру телефона + SMS-код (OTP, 4 цифры, TTL 5 мин, повторная отправка через 60 сек, лимит 3 кода/номер/час, 5 попыток ввода).
- Гость: просматривает каталог, ищет, наполняет корзину. Авторизация запрашивается на этапе оформления заказа и при входе в профиль/избранное/бонусы.
- JWT: access 30 мин, refresh 30 дней, refresh-ротация. Хранение — `flutter_secure_storage`.
- Удаление аккаунта из профиля (требование App Store / Google Play).

### 4.2 Главная
- Строка поиска (тап → экран поиска).
- Баннеры-слайдер (управляются из админки: картинка + ссылка на категорию/товар/подборку).
- Горизонтальные подборки: «Хиты продаж», «Новинки», «Со скидкой» (авто по данным: топ продаж, дата добавления, наличие old_price).
- Плитка корневых категорий.

### 4.3 Каталог и категории («как в Каспи»)
- Дерево категорий 2 уровня: экран каталога — слева список корневых, справа плитка подкатегорий с картинками (паттерн Kaspi Магазина).
- Категории с иконкой/картинкой, порядок и видимость — из админки.
- Ожидаемый объём: ~15–25 корневых, ~100–200 подкатегорий на 4000+ SKU.

### 4.4 Листинг товаров
- Grid 2 колонки. Карточка: фото, название (2 строки, ellipsis), цена, старая цена (перечёркнута), бейдж «~N ₸ бонусами», кнопка «+» (в корзину)/степпер.
- Сортировка: популярные (по умолчанию), цена ↑, цена ↓, новинки.
- Фильтры: цена (диапазон), «в наличии», атрибуты категории (например бренд, цвет — из `attributes` товаров, см. 10).
- Пагинация: infinite scroll по 24, скелетоны при загрузке.
- Товары с `stock = 0` показываются в конце с пометкой «Нет в наличии», кнопка неактивна.

### 4.5 Поиск
- Полнотекстовый по названию, артикулу (SKU), описанию. Устойчив к опечаткам и раскладке (pg_trgm), русский язык.
- Подсказки (suggest) от 2 символов, debounce 300 мс.
- История запросов — локально на устройстве (последние 10, очистка).
- Результаты = тот же листинг 4.4 (с фото). «Ничего не найдено» → показать хиты продаж.

### 4.6 Карточка товара
- Галерея фото (свайп, пинч-зум), название, артикул.
- Цена + старая цена; плашка «Вернём ~N ₸ бонусами» (расчёт по текущему уровню пользователя, для гостя — по базовому).
- **Остаток:** при `stock ≤ 10` — «Осталось X шт», иначе «В наличии»; при 0 — «Нет в наличии» + кнопка «Сообщить о поступлении» (вторая очередь, в MVP просто неактивная кнопка покупки).
- Характеристики — таблица из `attributes` (ключ–значение).
- Описание — сворачиваемый блок.
- «Похожие товары» — горизонтальная лента (см. 4.15).
- Кнопки: «В корзину» → степпер; избранное (сердечко).

### 4.7 Корзина
- Хранится **локально на устройстве** (без синка между устройствами в MVP).
- Позиции со степперами, свайп-удаление, сумма по позициям.
- Поле промокода → `POST /promo/validate`.
- Списание бонусов: поле/слайдер «Списать бонусы», максимум — по правилам 4.11.
- Блок итогов считает **только сервер**: `POST /cart/calculate` (товары + qty + промокод + бонусы) → актуальные цены, скидки, недоступные позиции, итог. Вызов при открытии корзины и любом изменении. Если цена/остаток изменились — показать плашку «Цены обновились».

### 4.8 Оформление заказа (checkout)
- Способ получения:
  - **Самовывоз** — адрес магазина, текст «Соберём в течение 2 часов в рабочее время».
  - **Доставка по Астане** — адрес (улица, дом, кв., комментарий), тариф из настроек админки (по умолчанию: 1500 ₸, бесплатно от 20 000 ₸).
- Получатель: имя + телефон (префилл из профиля).
- Оплата: только онлайн через Kaspi Pay (см. 4.9 и `kaspi_pay_integration.md`). Оплаты при получении нет: сначала оплата, потом сбор и передача.
- Кнопка «Оформить» → `POST /orders` → экран оплаты или экран «Заказ принят».

### 4.9 Онлайн-оплата и чек
- Платёжный провайдер подключается через **абстракцию `PaymentProvider`** (create_payment → payment_url, webhook → confirm), чтобы провайдера можно было заменить без переписывания заказа. Кандидаты и выбор — раздел 14, вопрос 1.
- Флоу: `POST /orders/{id}/pay` → `payment_url` → открытие в Chrome Custom Tab / SFSafariViewController → возврат по deeplink `app://payment-result` → приложение опрашивает `GET /orders/{id}` до финального статуса. Истина — **только webhook** от провайдера (подпись проверяем), редирект — просто UX.
- Статусы оплаты: `pending / paid / failed / refunded`. Неоплаченный заказ автоотменяется через 30 мин (фоновая задача), остатки возвращаются.
- **Фискализация (закон РК):** после `paid` — чек через ОФД-API (WebKassa или reKassa), ссылка на чек в деталях заказа и в push.

### 4.10 Заказы
- Список: номер (`ORD-2026-000123`), дата, сумма, статус, превью первых 3 фото.
- Детали: состав, суммы (товары / скидка / бонусы списано / доставка / итого), способ оплаты, ссылка на чек, статус-трекер.
- Статусы заказа: `new → confirmed → assembling → ready_for_pickup | delivering → done`; `cancelled`. Отмена пользователем — только в `new`.
- «Повторить заказ» — все доступные позиции в корзину.

### 4.11 Бонусная программа
- **Уровни кэшбэка по накопленной сумме выполненных заказов** (таблица настраивается в админке; по умолчанию):

| Накоплено покупок | Кэшбэк |
|---|---|
| 0 – 49 999 ₸ | 0% |
| 50 000 – 99 999 ₸ | 1% |
| от 100 000 ₸ | 3% |

- 1 бонус = 1 ₸. Начисление — при переходе заказа в `done`, **на сумму, оплаченную деньгами** (за вычетом скидок и списанных бонусов).
- Списание: до 30% суммы заказа (настраивается). Срок жизни бонусов: 180 дней (настраивается), сгорание — фоновой задачей, FIFO.
- При отмене/возврате заказа: начисленные бонусы снимаются, списанные — возвращаются.
- Экран «Бонусы»: баланс, текущий уровень, прогресс-бар «До уровня 3% осталось 12 400 ₸» (те самые «рекомендации по бонусам»), история операций (начислено/списано/сгорело, по какому заказу).

### 4.12 Промокоды
- Тип: процент или фикс. сумма; мин. сумма заказа; срок действия; лимит использований общий и на пользователя; флаг «совместим со списанием бонусов» (по умолчанию — да).
- Порядок расчёта: цена → промокод → списание бонусов. Бонусы начисляются на итог после всех скидок.
- Один промокод на заказ.

### 4.13 Профиль
- Личные данные: имя, телефон (только чтение), email, дата рождения (опционально).
- Разделы: Мои заказы, Бонусы, Избранное, Адреса доставки.
- **Поддержка:** кнопки «Позвонить» (`tel:`) и «WhatsApp» (`wa.me/<номер>?text=…` с преднабранным номером заказа, если открыто из заказа).
- О приложении, оферта, политика конфиденциальности (webview), выход, удаление аккаунта.

### 4.14 Push-уведомления (FCM)
- MVP-триггеры: смена статуса заказа; начисление бонусов; сгорание бонусов через 7 дней («У вас сгорит 1 200 бонусов»).
- Регистрация токена: `POST /devices`. Тап по push → deeplink на заказ/бонусы.

### 4.15 Рекомендации (MVP-версия)
- «Похожие товары» в карточке: та же подкатегория, в наличии, цена ±40%, сортировка по продажам, максимум 10.
- Подборки на главной — по правилам из 4.2.
- Co-occurrence «С этим покупают» — вторая очередь, когда накопятся заказы.

## 5. Вторая очередь (после MVP, по приоритету)

1. Маркетинговые push-рассылки из админки (сегменты: все / по уровню бонусов / неактивные 30 дней).
2. «С этим покупают» по co-occurrence заказов.
3. Отзывы и рейтинги (с модерацией в админке).
4. Казахская локализация.
5. «Сообщить о поступлении» + push при появлении остатка.
6. Синхронизация остатков с учётной системой (XLSX-обмен по расписанию или API, когда определимся с учёткой).
7. Тёмная тема.
8. Поиск по фото (если реально понадобится — через embedding-модель, отдельная оценка).

## 6. Админ-панель (Трек A)

**Стек:** React 18 + Vite + TypeScript + shadcn/ui + TanStack Query. Тот же API, эндпоинты `/api/v1/admin/*`. Auth: email + пароль, роли `admin` / `manager` (manager не видит настройки и пользователей).

**Модули:**

1. **Дашборд:** заказы сегодня/за неделю, выручка, средний чек, топ-10 товаров.
2. **Заказы:** список с фильтрами (статус, дата, оплата), детали, смена статуса, отмена (с автоворвратом бонусов), **кнопка «Накладная XLSX»** — генерация накладной по заказу (используем уже существующий openpyxl-пайплайн З-2).
3. **Товары:** таблица с поиском/фильтрами; форма товара (фото до 10 шт, drag-sort, категория, цена, старая цена, SKU, штрихкод, остаток, описание, характеристики ключ–значение, видимость).
   - **XLSX-импорт — критичный модуль для 4000+ SKU:** шаблон-файл с колонками (sku, name, category_path, price, old_price, stock, barcode, description, attr:*); режим «создать или обновить по SKU»; **dry-run с отчётом ошибок** (несуществующая категория, дубли SKU, битые цены) до применения; лог импортов.
   - XLSX-экспорт текущего каталога тем же шаблоном.
   - Массовые операции: изменить цены на ±N% по категории, обнулить/установить остатки по выбранным.
4. **Категории:** дерево, drag-n-drop порядок, картинка, видимость.
5. **Баннеры:** картинка, ссылка (категория/товар/URL), порядок, вкл/выкл, период показа.
6. **Промокоды:** CRUD по полям из 4.12, счётчик использований.
7. **Бонусы:** таблица уровней (порог → %), лимит списания %, срок жизни; ручная корректировка баланса пользователя с обязательным комментарием (пишется в историю операций).
8. **Пользователи:** поиск по телефону/имени, карточка: заказы, бонусы, блокировка.
9. **Настройки:** контакты магазина, адрес самовывоза, тарифы доставки, вкл/выкл «оплата при получении», номер WhatsApp поддержки, тексты оферты/политики.

## 7. Нефункциональные требования

- **Производительность:** листинг/поиск p95 < 300 мс на API (каталог кэшируется в Redis, инвалидация при изменении товара); первый экран приложения интерактивен < 2 с на среднем устройстве и 4G.
- **Изображения:** при загрузке в админке сервер генерирует 3 размера WebP (thumb 200px, card 500px, full 1200px); отдача через nginx с длинным Cache-Control; в приложении `cached_network_image`.
- **Масштаб:** закладываемся на 20 000 SKU, 10 000 пользователей, 100 одновременных — PostgreSQL + Redis на текущей инфре хватает с запасом.
- **Надёжность:** ежедневный `pg_dump` → S3-бакет (хранение 30 дней), миграции только через Alembic, staging идентичен prod по конфигу.
- **Безопасность:** HTTPS везде; rate limit на OTP и на `POST /orders`; цены/скидки/бонусы считает только сервер; админка — отдельный поддомен, вход по IP-allowlist или VPN (решает Трек A); секреты в k8s Secrets; в логах нет телефонов и токенов.
- **Законодательство РК:**
  - персональные данные граждан РК — БД на серверах **на территории РК** (Закон «О персональных данных и их защите», требование локализации). Прод-БД размещаем у казахстанского провайдера — раздел 14, вопрос 5;
  - онлайн-платежи — обязательный чек ОФД (4.9);
  - в приложении: публичная оферта, политика конфиденциальности, согласие на обработку ПДн при регистрации.
- **Аналитика и мониторинг:** Firebase Analytics + Crashlytics (обязательно с первого билда); backend — structured-логи, `/health`, Sentry (или хотя бы алерт в Telegram на 5xx).

## 8. Дизайн (минимализм)

## 10. Модель данных (ядро, PostgreSQL)

```

categories(id, parent_id, name, slug, image, sort, is_active)
products(id, category_id, sku UNIQUE, barcode, name, slug, description,
         price INT, old_price INT NULL, stock INT, attributes JSONB,
         images JSONB, sales_count INT, is_active, created_at, updated_at)
banners(id, image, link_type, link_value, sort, is_active, starts_at, ends_at)
favorites(user_id, product_id, PK(user_id, product_id))
orders(id, number UNIQUE, user_id, status, payment_method, payment_status,
       delivery_type, address JSONB, recipient_name, recipient_phone,
       items_total INT, promo_code, promo_discount INT, bonus_spent INT,
       delivery_price INT, total INT, bonus_earned INT,
       receipt_url, created_at, updated_at)
order_items(id, order_id, product_id, name, price INT, qty, sum INT)  -- снапшот цены
promo_codes(id, code UNIQUE, type, value, min_order INT, valid_from, valid_to,
            usage_limit, per_user_limit, used_count, stacks_with_bonus, is_active)
promo_usages(id, promo_id, user_id, order_id, created_at)
bonus_accounts(user_id PK, balance INT, lifetime_spent INT)  -- lifetime_spent определяет уровень
bonus_transactions(id, user_id, order_id NULL, amount INT, type,  -- accrual|redeem|expire|adjust|revert
```

Остатки: списание при создании заказа (резерв), возврат при отмене/автоотмене — в одной транзакции, `SELECT … FOR UPDATE` на строки товаров.

## 13. Критерии приёмки MVP (чек-лист, прогоняем вдвоём)

**Покупатель:**
1. Находит конкретный товар из 4000+ тремя путями: категории, поиск с опечаткой, поиск по артикулу — везде < 3 сек.
2. Открывает карточку: фото, цена, бонус-плашка, характеристики, остаток, похожие.
3. Собирает корзину из 3+ позиций, применяет промокод, списывает бонусы — итог совпадает с ручным расчётом по правилам 4.11–4.12.
4. Оформляет самовывоз и доставку; оплачивает онлайн; получает push и видит чек ОФД в заказе.
5. Отмена неоплаченного заказа возвращает остатки и бонусы.
6. Заказ доводится админом до `done` → бонусы начислены, уровень пересчитан, прогресс-бар обновился.
7. Регистрация нового номера, выход, вход, удаление аккаунта — работают.

**Админ:**
8. Импортирует XLSX на 4000+ строк: dry-run показывает ошибки, импорт < 2 мин, товары видны в приложении.
9. Меняет цену и остаток товара → в приложении обновилось (кэш инвалидирован).
10. Ведёт заказ по статусам, скачивает накладную XLSX, отменяет заказ.
11. Меняет таблицу бонусных уровней → плашки в приложении пересчитались.

**Технически:**
12. Цены, подставленные клиентом в запрос, игнорируются (проверка руками через curl).
13. Webhook с неверной подписью отклоняется; повторный webhook не задваивает оплату/бонусы (идемпотентность).
14. Бэкап БД снимается и восстанавливается на staging.
15. Crashlytics и аналитика получают события с обоих платформ.

## 14. Открытые вопросы (закрыть в Спринт 0)

1. **Платёжный провайдер.** Kaspi Pay (родной для покупателя, но нужен договор и доступ к API под ИП) vs агрегатор типа Freedom Pay (быстрый старт, карты + Apple/Google Pay, комиссия выше). Решение: собрать условия обоих за первые 3 дня; архитектурно всё равно идём через `PaymentProvider`, так что можно стартовать с одного и добавить второго.
2. **Название, бренд, акцентный цвет** приложения (нужны для иконки, сплэша и сторов).
3. **Доставка:** кто возит (сами/курьерка), тарифы и зона по Астане, сроки.
4. **Остаток на карточке:** точное число всегда или «Осталось X» только при ≤ 10 (текущий дефолт в 4.6)? Уточнить у заказчицы.
5. **Хостинг прод-БД в РК:** выбрать провайдера (ps.kz, hoster.kz, QazCloud — сравнить VPS с NVMe). Staging можно оставить на текущем VPS.
6. **Оплата при получении:** включаем в MVP или только онлайн?
7. **Источник данных:** откуда берём 4000 позиций (выгрузка из текущей учётки?) и, главное, **фото** — есть ли, в каком качестве, кто добивает недостающие. Это самый частый блокер запуска — оценить в первые дни.
8. **ОФД:** какой сервис уже используется в рознице (чтобы чеки онлайн-магазина шли туда же) — WebKassa / reKassa / иной.
